# Ascend 环境部署工具：需求分析与开发计划

## 1. 现有流程与约束

已阅读 `reference/environment/` 下全部六个文件。现有流程是：在 Windows 打开固定版本的下载链接，手工保存文件；用 SSH/SCP 上传到 Linux 服务器；在服务器上用 `build-image.sh` 校验文件名及版本并构建镜像；最后用固定的 Compose 文件启动容器。

| 文件 | 可复用内容 | 当前限制 |
| --- | --- | --- |
| `open-downloads-windows.ps1` | CANN 9.1.0、Torch 2.10.0 和 TorchNPU 2.10.0.post4 的示例下载地址 | 仅打开链接；版本与型号写死；一次列出多个型号 |
| `upload-windows.ps1` | SSH/SCP 上传、远端建目录、SHA256 传输校验 | 文件名与目录固定；无打包；只接受较窄的路径格式 |
| `build-image.sh` | Toolkit/ops 型号与版本匹配校验、wheel 校验、基础镜像架构检查 | 固定 Python 3.10、x86_64/amd64；仅接受本地已有基础镜像；临时复制大文件 |
| `Dockerfile`、`entrypoint.sh` | 多阶段构建、CANN 环境加载 | Ubuntu 22.04 和特定镜像源逻辑；依赖固定 wheel 标签 |
| `docker-compose.yaml` | NPU 设备及驱动挂载的示例 | 镜像、容器名、设备节点、项目目录均固定 |

现有脚本给出的是一个已知组合，不能据此推断任意 Toolkit 版本都有相同的下载路径、ops 包或匹配的 TorchNPU wheel。版本目录必须维护受支持组合并校验链接，未知组合应报告缺失而不是拼出未经验证的 URL。

## 2. 产品边界与方案

静态 HTML/JS 不能直接访问用户文件系统、持有 SSH 会话、运行 Docker 命令或提供容器 PTY。因此采用**静态前端 + 本地辅助服务**：前端可作为静态文件提供；辅助服务在用户机器运行，向本机回环地址提供受限 API。辅助服务使用 SSH/SFTP 操作目标 Linux 服务器，构建和启动 Docker 均在目标服务器执行。页面显示任务进度和日志，终端通过 WebSocket 桥接 SSH PTY 与浏览器终端组件。

建议使用 Node.js 实现辅助服务与静态文件服务，统一处理流式下载、归档、SSH/SFTP、WebSocket 与终端。终端前端可用 xterm.js。部署时页面只连接本机辅助服务，不直接接触 SSH 私钥。辅助服务仅监听 `127.0.0.1`，任务参数用结构化 API 传入，不拼接不受信任的 shell 命令。

### 核心流程

1. **选择版本**：输入 Toolkit 版本、NPU 算子型号（如 910B/950），同时明确目标服务器 CPU 架构。版本目录给出 Toolkit、对应 ops、Torch、TorchNPU 四个文件的官方来源、期望文件名及兼容关系；在界面中展示并检查可访问性。
2. **准备文件**：下载到本地缓存，支持重试和断点续传；记录来源、大小和 SHA256。将恰好需要的四个包、生成配置、模板文件及校验清单打成一个归档，并允许用户下载归档。若官方提供校验值，优先与官方值核对；本地 SHA256 仅用于上传后的一致性检查。
3. **同步远端**：配置 `user@host`、SSH 端口、认证方式和服务器工作空间。测试 SSH 连接、检查路径写权限及容量；按任务 ID 创建独立构建目录；上传归档、校验哈希并解包。失败可重试，原有构建目录不被静默覆盖。
4. **构建镜像**：配置目标服务器上可用的基础镜像和镜像标签；预检 `docker info`、Compose 可用性、磁盘空间、基础镜像架构和必需文件。生成 Dockerfile 与构建参数后在远端执行构建，实时回传日志和最终镜像 ID。Docker 权限以该 SSH 用户实际运行 `docker info` 的结果判定，不以是否属于 `docker` 组单独判定；失败时说明权限或 daemon 问题，不自动使用 `sudo`。
5. **启动与终端**：根据所选 NPU 设备、宿主机驱动路径、项目源码路径和工作目录生成 Compose 文件；先做配置校验，再执行 `docker compose up -d` 并检查容器状态。页面打开交互式终端，SSH PTY 执行 `docker compose exec`；支持输入、窗口尺寸变化、断线提示及重连。

### 必需的配置分层

- **版本目录**：CANN Toolkit/ops 版本、NPU 算子型号、CPU 架构、Torch/TorchNPU/Python 兼容组合以及可信下载 URL。
- **目标服务器**：主机、端口、用户名、认证方式、远端工作空间和 Docker 配置。
- **容器运行**：基础镜像、镜像标签、NPU 设备列表、驱动挂载路径、项目源码挂载路径、容器工作目录。

首版建议只支持参考脚本可验证的 **Linux x86_64 / amd64、Python 3.10、Ubuntu 22.04 基础镜像**以及经过核实的 CANN 组合。其他架构、基础发行版和版本组合需要单独的模板或兼容性数据，不应通过改一个版本字符串直接启用。

## 3. 开发阶段

| 阶段 | 交付物 | 完成标准 |
| --- | --- | --- |
| 0. 基线与接口 | 仓库结构、参考脚本、配置 schema、任务状态机和 API 草案 | 输入、产物及失败状态有明确定义；仓库可本地启动 |
| 1. 版本选择与归档 | 静态页面、版本目录、URL 校验、下载器、SHA256 清单、归档 | 已支持组合只下载所选型号；未知或失效链接明确报错；归档可校验并解包 |
| 2. 远端同步 | SSH 连接测试、远端目录创建、SFTP 上传、哈希复核 | 用户可指定服务器和工作空间；中断后可安全重试；文件在远端完整 |
| 3. 镜像构建 | Dockerfile 生成、Docker 权限与基础镜像预检、远端构建日志 | 无 Docker 权限时在构建前停止；成功时记录镜像 ID；失败日志可查看 |
| 4. Compose 与终端 | Compose 生成、配置校验、容器启动、WebSocket/PTY 终端 | 容器健康状态可见；能交互执行命令；关闭页面后 SSH 会话被清理 |
| 5. 验收与文档 | 单元/集成测试、真实 NPU 主机冒烟测试、部署和故障排查说明 | 四步主流程及失败恢复均通过；实际设备可在容器内识别 |

实施顺序按阶段推进，每阶段都保留可查看的生成文件和日志，不让页面只显示“成功/失败”而无法定位问题。

## 4. 接口与安全约束

- API 至少覆盖：版本目录查询、下载与归档任务、SSH 连接测试、远端同步、预检、构建、Compose 生成与启动、终端 WebSocket、任务日志与取消。
- 对 URL 使用受信任域名或受支持目录清单；对版本、镜像名、端口、设备节点和路径做服务端校验。SSH 的主机密钥需要首次确认与后续严格校验。
- 凭据只保存在本地辅助服务的内存或用户已有的 SSH 代理/密钥文件中；日志不输出密码、私钥和敏感环境变量。镜像构建、容器启动及远端目录写入都由用户在界面中主动触发。
- 每个任务使用独立目录和状态记录；下载缓存与归档可清理，已构建镜像和容器不随任务失败自动删除。
- 超大安装包采用流式传输，并在下载前检查本地空间，在上传/构建前检查远端空间；避免把大文件全部读入内存。

## 5. 待确认的产品参数

这些参数不阻碍阶段 0–1 的实现，但会影响后续真实主机验收：

1. 首版应支持的 Toolkit 版本、NPU 型号，以及对应 Torch/TorchNPU 组合。参考资料目前只明确给出 9.1.0、910/910B/950 和 Torch 2.10.0 组合。
2. 目标服务器的 CPU 架构、Linux 发行版、Docker/Compose 版本、NPU 设备和驱动挂载路径。
3. 项目源码是已经存在于目标服务器，还是也要与安装包一起上传；现有 Compose 示例假定目标服务器已有 `PROJECT_ROOT`。
4. 用户希望辅助服务运行在操作员电脑，还是目标服务器。上述计划默认在操作员电脑运行，并通过 SSH 访问目标服务器。
